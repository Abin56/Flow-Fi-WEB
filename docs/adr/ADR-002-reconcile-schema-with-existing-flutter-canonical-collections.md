# ADR-002: Reconcile generalized Firestore schema with existing Flutter-canonical collections

**Status:** Accepted
**Date:** 2026-08-02
**Backlog task:** M1-T1 (Firestore schema + rules)
**Architecture section(s) affected:** §19 (Firestore Data Model), §19.1 (migration note), §19.2 (relationships), §9 (implicitly — "Module: Credit Card Statements" now maps onto a real entity), §18/§28.9 (Import Engine's account-balance update target)

## Context

Architecture v1.0 designed `accounts/{accountId}`, `financialDocuments/{documentId}`, and `documentRecords/{recordId}` as new, top-level collections (each carrying a `userId` field for scoping), on the assumption of a greenfield schema. Implementation of M1-T1 discovered this is not a greenfield project:

- `lib/firestore/collections.ts` is a **direct, byte-identical port of the Flutter app's `FirestoreCollections` Dart constants** — every collection lives under `users/{userId}/{collection}` (never top-level + a `userId` field), and this pattern is load-bearing: "both apps read/write the same documents."
- The credit card entity already has a reserved, Flutter-canonical name and shape: `users/{uid}/creditCards/{cardId}`, with a `statements` **subcollection** underneath it (`users/{uid}/creditCards/{cardId}/statements/{statementId}`), and a `statementPayments` subcollection under that. `lib/engines/credit-utilization.ts` already implements the real business logic against this shape (`UtilizationCard`, `UtilizationStatement`, `UtilizationEmi`), ported from `credit_card_providers.dart`.
- A generic `Account` model already exists and is real (not mock) — `lib/models/account.ts`, `AccountRepository` — for `type: "cash" | "bank" | "card" | "wallet" | "business" | "other"`. This is a *different* concept from `creditCards`: it's the simple, cross-type account ledger, while `creditCards` is the richer, credit-specific entity (statement cycles, EMI linkage, shared limits). Neither of these is what Architecture §19's generic `accounts/{accountId}` collection described.
- Crucially, a credit card's outstanding/available balance is **not a stored, mutable field** the way `Account.currentBalance` is. It is *computed on read* from `statements` + `emis` via `creditCardStanding()` (§ engine already exists). There is no `creditCards/{cardId}.currentBalance` field to transactionally update.
- `lib/models/credit-card.ts` does not exist yet ("shapes mirror the eventual real domain types (`lib/models/credit-card.ts`) loosely" — comment in `lib/mock/credit-cards-data.ts`) — the Credit Cards feature is currently mock-data-only, not yet Firestore-wired. So this collection is real (reserved, named, and load-bearing for future Flutter parity) but not yet built in this repo.
- `transactions` already exists as the single canonical collection every finance engine (cash-flow, net-worth, budgets, reports) reads. Architecture §19's `documentRecords/{recordId}` would be a second, parallel "transaction-shaped" collection — which directly conflicts with the validated architecture principle "no duplicated business logic" (§29) if committed transactions from statement imports don't flow through the same collection and repository every other transaction does.

None of this contradicts the *pipeline* the architecture describes (§2, §10, §18) — Detection → Parse → Confidence → Merchant/Category → Dedupe → Review (staging) → Import (commit) → Business Logic → Firestore is unaffected. What's affected is purely §19's collection layout and naming, which was written without visibility into the existing schema.

## Decision

The following path mapping supersedes Architecture §19's literal collection names for implementation purposes. The pipeline stages, staging/live split, and confidence-driven review model are unchanged.

| Architecture §19 concept | Reconciled real path | Notes |
|---|---|---|
| `accounts/{accountId}` (credit-card-typed) | `users/{uid}/creditCards/{cardId}` | New model/repository to be ported here (`lib/models/credit-card.ts`), following the exact pattern of `lib/models/account.ts`. This is the "account" the Upload flow's card selector (§4.1 Screen 1) lists. |
| `financialDocuments/{documentId}` metadata + archive fields | `users/{uid}/financialDocuments/{documentId}` | Stays a distinct collection (uploads/parses are not the same lifecycle as a Statement business record — see below) — only the path prefix changes, to match every other collection's `users/{uid}/...` convention. |
| `financialDocuments/{id}/importHistory`, `/versionHistory`, `/changeLog` | `users/{uid}/financialDocuments/{id}/importHistory` etc. | Unchanged shape (§14.1 fix), just nested under the corrected parent path. |
| The *business record* a committed statement produces (due date, totals, payment status) | `users/{uid}/creditCards/{cardId}/statements/{statementId}` — **existing subcollection** | The Import Engine's commit step (§18) creates/updates a doc here, using whatever shape `UtilizationStatement` already implies (`periodStart`, `periodEnd`, `dueDate`, `totalAmount`, `amountPaid`, `remainingAmount`, `isPaid`/`status`). `financialDocuments` holds parser provenance (fileHash, storagePath, detectedSource, parserConfidence, registryVersion) and links to this statement via a `statementId` field; it does not duplicate the statement's business fields. |
| `documentImports/{importId}` (staging) | `users/{uid}/documentImports/{importId}` | New collection, no existing conflict — only the path prefix changes. |
| `documentImports/{id}/records/{recordId}` (staged rows) | `users/{uid}/documentImports/{importId}/records/{recordId}` | Unchanged shape, corrected path. |
| `documentRecords/{recordId}` (LIVE, post-commit) | **Existing `users/{uid}/transactions/{transactionId}` collection** — no new collection | The Import Engine commits staged records as real `Transaction` docs via the existing `transactionToFirestore`/`TransactionRepository`, so every existing engine (cash-flow, net-worth, budgets, reports) picks them up with zero new integration work. Additive, optional fields are appended to the `Transaction` shape: `sourceStatementId`, `sourceImportId`, `merchantRaw`, `confidenceScore`. See "Consequences" below for the Flutter-compatibility caveat this requires. |
| `merchantMappings/{id}` (`scope: "global" \| "user:{userId}"`) | Split by location instead of by field: `merchantMappings/{id}` (top-level, global only) and `users/{uid}/merchantMappings/{id}` (personal only) | Firestore-idiomatic — avoids a manually-filtered `scope` field and lets security rules express the global-vs-personal boundary structurally (global: read-only to clients per §28.5's corroboration-gate finding; personal: owner read/write). |
| `parserHistory/{id}` | `users/{uid}/parserHistory/{id}` | Diagnostics data, but still per-user — moved under the user for consistency and to avoid an unscoped top-level collection needing its own bespoke rule. |
| `aiInsights/{id}` | `users/{uid}/aiInsights/{id}` | Path prefix corrected, shape unchanged. |
| `documentTypeRegistry/{documentType}` | `documentTypeRegistry/{documentType}` — **unchanged, stays top-level** | Genuinely global config, not per-user data — this one was already correctly modeled in §19. |

**Balance-update consequence (affects M9-T1/M9-T2 directly):** Architecture §18/§28.9 described the Import Engine transactionally updating `accounts/{accountId}.currentBalance`. For the credit-card module, there is no such field to update — utilization/available credit is computed at read time by the existing engine. M9-T2's required fix (a Firestore transaction guarding concurrent writes) still applies, but its **target changes**: the transaction must guard concurrent create/update of the specific `users/{uid}/creditCards/{cardId}/statements/{statementId}` document (two near-simultaneous imports for the same statement period), not a card-level balance field. This is recorded here rather than by editing §18/§28.9, per this project's rule that the locked architecture is never edited — implementers should read "`accounts/{accountId}.currentBalance` update" in §18/§28.9 as "`creditCards/{cardId}/statements/{statementId}` transactional create/update," per this ADR, for the credit-card module specifically.

## Consequences

- M1-T1's Firestore rules and TypeScript models are written against this reconciled path table, not §19's literal names.
- `lib/models/credit-card.ts` and a `CreditCardRepository` (mirroring `lib/models/account.ts` / `AccountRepository`) become part of M1-T1's scope — they didn't exist before this task and the Statement Intelligence feature cannot select a card (§4.1 Screen 1) without them.
- **Flutter-compatibility caveat:** adding `sourceStatementId` / `sourceImportId` / `merchantRaw` / `confidenceScore` to the `Transaction` shape is additive (new optional fields), which is safe for any Firestore reader that ignores unknown fields — but this has **not been verified against the actual Flutter `Transaction` model's deserialization behavior** (strict vs. lenient parsing). This is flagged as an open risk, not silently assumed safe: before Milestone 9 (Import Engine) writes real `Transaction` docs with these new fields, confirm with whoever owns the Flutter codebase that its Firestore converter tolerates unknown fields, or add the fields there too. Tracked as a blocking pre-check for M9-T1, not resolved by this ADR alone.
- No pipeline stage, no confidence-engine behavior, no duplicate-detection algorithm, and no Review Workspace UX from Architecture §0–§27 changes. This ADR is entirely a path/collection-naming reconciliation plus one balance-update-target correction — the shape of the system is unchanged.
- Firestore security rules (M1-T1) must now cover the *entire* existing schema (`users/{uid}/{accounts,transactions,categories,budgets,savingsGoals,people,bills,loans,emis,expenses,paymentSchedules,creditCards,sharedCreditLimits,...}`), not just the new collections — since no `firestore.rules` file previously existed in this repo to extend. Writing rules for only the new collections would risk shipping an incomplete ruleset if this file becomes the deployed source of truth. This is called out explicitly in the M1-T1 implementation, not silently assumed.

## Alternatives considered

- **Create the generic `accounts`/`financialDocuments`-as-statement/`documentRecords` collections exactly as architected, alongside the existing schema.** Rejected — this produces two parallel, competing representations of the same real-world entities (a credit card would exist in both `creditCards` and `accounts`; a transaction would exist in both `transactions` and `documentRecords`), which directly violates the "no duplicated business logic" property the architecture itself validated in §29. It would also mean Flutter and Web read genuinely different data for the same feature, breaking "one brain, many surfaces" (§1).
- **Migrate the existing `creditCards`/`statements`/`transactions` collections to the architecture's generic names.** Rejected — these are live, Flutter-canonical, and the Flutter app is out of scope for this backlog; a rename would require coordinated cross-repo migration far outside "implementation-driven refinement" and would need to go back through design/RFC, not an ADR.
