# Transaction Studio — Critical UX Review

**Grounding note before the review:** I read the actual codebase, not just the vision doc. The finding that reframes this whole review: **the grid doesn't exist yet.** `/statement-review` today is an upload-and-status-tracker page; staged rows render as a plain read-only `<div>` list with two columns (merchant + amount). The data model (`StagedRecord`), the backend intelligence (confidence, duplicate, category, tag, merchant engines), and even the write layer (`useTransactionStudioMutations`) are all built and mostly unused. So this review isn't critiquing a half-built grid — it's critiquing **the spec that's about to become one**, using the data model as ground truth for what's actually available to design with.

One more finding that has to be flagged before anything else: **there are two different, incompatible column lists in this project right now.** The vision doc (`docs/statement-workspace-vision.md`) specifies `Select · Date · Merchant · Description · Amount · Debit/Credit · Suggested Category · FlowFi Account · Expense Type · Person · Split Status · Tags · Confidence · Status · Actions`. Your prompt's list is `Include, Date, Merchant, Amount, Action, Action Details, Owner, Split, Category, Tags, Notes, Commit Status`. These aren't the same spec — the vision doc separates Debit/Credit from Amount and has no "Notes" or "Action Details," while your list collapses several vision-doc columns into `Action`/`Action Details` and adds `Notes`. **Your list matches the actual `StagedRecord` schema far better** (`action`, `actionDetail`, `owner`, `notes`, `tags` are real fields; `Description`, `FlowFi Account`, `Person` as separate vision-doc columns are not literal field names). I'm treating your list as current intent and flagging the vision doc as stale — but someone needs to reconcile these before implementation, or two people will build to two different specs.

---

## 1. UX Review

**The core interaction model is undecided, and that's the actual risk — not row styling.** A spreadsheet needs an answer to: what is a "cell," what does clicking a cell do, what does clicking a row do, and how does focus move. Right now none of that exists in code and the vision doc doesn't specify it either. Before any visual polish, three decisions have to be made:

- **Cell-level vs. row-level editing.** True Excel/Airtable behavior is cell-level: click a cell, it becomes the edit target, arrow keys move a focus rectangle between cells (not rows). Given `Action`/`Action Details` are a coupled pair (Action determines what Action Details even means — split needs participants, EMI needs term/rate, transfer needs a destination account), those two columns can't be edited independently with a plain cell editor. This needs a **compound cell**: clicking `Action Details` should behave differently depending on the current `Action` value — for most Actions it's inert or shows a summary chip, for Split/EMI/Loan/Transfer it opens a small structured editor (in-cell popover, not full modal). This is the single hardest interaction in the entire grid and it's not designed yet.
- **Row height / density.** Financial review grids live or die on density — a user reviewing 80 transactions from a statement wants to see 25+ rows without scrolling. A comfortable Airtable-style row (32-36px) with single-line truncated Merchant, right-aligned tabular-numeral Amount, and compact chips for Category/Tags/Status should be the default, with a "comfortable" density toggle as a stretch goal, not the default.
- **What triggers a save.** With Firestore writes per field and `useTransactionStudioMutations` already doing optimistic updates, the review needs to decide: does every keystroke debounce-save, does blur-commit save, or does the row batch all its dirty fields and save on a explicit "commit row" action? Blur-commit (like Notion/Airtable) is the right default — it's forgiving of partial edits and matches the optimistic-update pattern already built.

**Sticky/frozen columns need a firm decision, not "some columns are sticky."** With 12 columns, horizontal scroll is inevitable on anything narrower than an ultrawide monitor. Freeze `Include` (checkbox) + `Date` + `Merchant` on the left, and freeze `Commit Status` + a row-actions affordance on the right. Everything else (Amount, Action, Action Details, Owner, Split, Category, Tags, Notes) scrolls in the middle. This mirrors Excel's "freeze panes" and Airtable's primary-field-pinning — don't invent a new pattern here.

**The existing `FinanceTable` is not a safe foundation.** It's a hand-rolled flex grid with fixed inline-px column widths, no virtualization, no cell focus model, and read-only accessor cells. If Transaction Studio gets built by extending `FinanceTable`, it inherits all of that and the "spreadsheet-grade" bar becomes unreachable without a rewrite later. **Recommend deciding now** whether to build genuinely new grid infrastructure (even hand-rolled, but with a real cell/focus model and virtualization from day one) rather than stretching `FinanceTable` to do something it wasn't designed for.

## 2. Missing Features (things the spec is silent on that a premium grid can't ship without)

- **Confidence surfacing.** The backend computes a per-field confidence score and a row-level `needsReview` boolean (threshold 0.75, "cap don't average" across required fields), and `architecture.md` explicitly promises a collapse/expand UX built on it ("≥90% of records auto-verified/collapsed"). None of your 12 requested columns show this. This is the single highest-leverage backend signal with zero UI surface, and it's the mechanic that makes reviewing 80 rows feel like reviewing 8 (only the flagged ones need attention). This has to be in the design — either as a persistent `Confidence` column/indicator or as the row's default collapsed/expanded state. I'd argue for **not** a dedicated column (see §Columns below) but a left-edge indicator + default collapse state.
- **Duplicate detection surface.** Backend produces 4 duplicate types with human-readable reasons ("Same merchant, amount, and date as an already-imported transaction"). This needs a visible badge/chip on the row and a way to see the matched transaction without leaving the grid (inspector panel, see below). Currently zero surface.
- **Validation panel.** Vision doc §9 calls for a pre-import summary: unknown merchants, duplicates, low-confidence rows, missing categories/accounts/people, split errors. This is a distinct UI surface from the grid itself (a collapsible panel or the footer bar expanding into a checklist) and isn't accounted for in your column list because it's not a column — it's a gate on the "Approve & Import" action. Needs explicit design.
- **Row-level provenance / "show source."** `StagedRecord` carries `sourcePage`/`sourceLineIndex`. For a *review* tool built on trust ("did the parser read this right?"), the ability to jump to the source PDF page/line for a given row is high-value and currently has no UI hook at all. Worth a small icon-button per row that opens the PDF at that page.
- **Concurrent-edit warning.** `lastEditedAt`/`lastEditedBy` exist on the model specifically for this (multi-device/multi-tab editing of the same statement). No design exists. Minimum viable: a toast/banner if a row you're viewing was edited elsewhere since you loaded it.
- **Undo/redo.** Explicitly anticipated in code comments, not designed. For a grid where a single bulk-edit can touch 80 rows, undo is not a nice-to-have — one fat-fingered bulk action without undo will erode trust in "safe to experiment" fast. Needs at minimum a single-level "Undo last action" toast (Notion/Airtable pattern: action completes, toast shows for ~6s with an Undo button), even if a full multi-step undo stack is deferred.
- **Duplicate-signal naming collision.** `duplicateOfTransactionId` (resolved/confirmed) and `duplicateCandidateOf` (unresolved candidate) are two different backend fields. The grid needs one visual language that clearly distinguishes "we're confident this is a dupe, review recommended" vs "confirmed duplicate, already handled" — don't let two backend field names become two inconsistent UI treatments.

## 3. Recommended Improvements — Column by Column

Going through your 12 columns critically, in order:

- **Include** — correct as a leading checkbox column, correct to default `true`. One addition: needs a **header checkbox with tri-state** (all/none/some included) plus a footer count ("74 of 80 included"). Don't just put a checkbox in the header that does select-all — `Include` and "row is selected for bulk-editing" are two different concepts (one is "will this be imported," the other is "which rows is my current bulk edit targeting") and conflating them is a classic spreadsheet-clone mistake. You need **two separate selection mechanisms**: a leftmost `Include` checkbox (import decision) and a *second*, distinct row-select affordance (bulk-edit targeting) that only appears on hover or when the multi-select mode is active — like Airtable's row-hover checkbox vs. Gmail's star. Reusing one checkbox for both will confuse "I excluded this row" with "I selected this row to bulk-tag."
- **Date** — fine, freeze it. Add: sort indicator, and clicking the column header should toggle sort (statements aren't always chronological after parsing, and re-sorting by date is the single most common first action a user takes).
- **Merchant** — should show `counterpartyNormalized` primary, `counterpartyRaw` as a subtle secondary/tooltip when they differ (currently the raw fallback exists but there's no visual distinction between "we normalized this confidently" and "we're just showing you the raw statement text because normalization failed" — that difference is exactly the kind of thing confidence exists to communicate, and today it's invisible).
- **Amount** — right-align, tabular-nums (already the pattern in `DocumentImportRecordsList`, keep it), signed color (credit/debit) — good, this part is already right. Missing: currency shouldn't be assumed — `StagedRecord.currency` exists per-row; if a user has multi-currency cards, Amount needs a currency indicator, not just a symbol baked into formatting.
- **Action** — this is correctly identified in the code comment as "single source of truth," and it should be the most prominent editable column after Merchant/Amount. It's a 15-value enum — this must be a **searchable combobox**, not a plain `<select>`, or it will be miserable to use at 80-row scale. Grouping the enum visually (Expense-type actions / Transfer / Loan-EMI / Recurring / Investment / Ignore) inside the dropdown will help a lot.
- **Action Details** — as discussed in §1, this is the hardest cell in the grid. Design recommendation: render as a **summary chip** when collapsed ("Split 3 ways", "EMI · 12mo · 8.5%", "→ Savings Account") and expand into a structured inline editor on click. Never a raw JSON-ish text field.
- **Owner** — fine as a column (`me`/`shared`/`someone_else`/`transfer`), but it overlaps semantically with `Action` when Action is `shared_expense`/`transfer` — worth checking whether `Owner` should auto-set (and lock, or soft-suggest) when certain Actions are chosen, rather than being independently editable and possibly contradicting Action. Right now nothing enforces that consistency at the model level either — that's worth a validation-panel rule (§Missing Features above), not just a UI nicety.
- **Split** — should not be a fully separate column from `Action`/`Action Details` given `shared_expense` already carries split participants in `actionDetail`. Recommend collapsing `Split` into the `Action Details` summary chip ("Split 3 ways · $12 to you") rather than a 13th independent column that duplicates data already in Action Details. If kept separate for scannability, it must be read-only/derived, never independently editable — two places to edit the same fact is a data-integrity bug waiting to happen.
- **Category** — should be a combobox pre-filled from `suggestedCategory` (backend already computes this, currently unsurfaced) with a **visibly different treatment for "system-suggested, unconfirmed" vs "user-confirmed."** This is probably the single most impactful un-designed detail: if suggested categories look identical to user-picked ones, users will never know how much the system already got right, which undercuts the "effortless review" premise the whole feature is built on. Suggest: suggested-but-unconfirmed shows as a lighter/outlined chip; once touched or explicitly accepted, it solidifies.
- **Tags** — multi-value chip input, standard pattern, no notes beyond: pre-fill from `suggestedTags` with the same unconfirmed/confirmed visual distinction as Category.
- **Notes** — fine as a column, but a free-text column in a dense grid is awkward (either truncates uselessly or blows out row height). Recommend: a small icon/indicator in a narrow Notes column that opens the full text in the inspector panel or a popover, rather than an inline text cell competing for grid width. Reserve inline-editable-in-cell for short structured fields; Notes is the one column that's genuinely better handled outside the grid body.
- **Commit Status** — freeze on the right with row actions. Should reflect `committedTransactionId` (imported) vs `needsReview` vs default. This is your best real estate for the confidence signal too, if you don't want a dedicated Confidence column (see below) — a combined status chip that says "Ready" / "Needs review · low confidence on Amount" / "Imported" is more useful than a separate always-visible numeric confidence column that most users will never look at.

**On Confidence specifically:** I'd recommend *against* adding it as a 13th always-visible column. It's a mechanism (drives default row collapse/expand and feeds into Commit Status), not something users want to stare at as a number for every row. Surface it as: (a) the row's default expand/collapse state, (b) a small indicator dot/icon next to whichever specific field is low-confidence (per the architecture doc's own spec: "that specific field highlighted, not the whole row flagged generically"), and (c) folded into the Commit Status chip. This keeps the 12-column count intact while still surfacing the signal — adding it as a literal column both bloats an already-wide table and buries the actually-useful part (which field, specifically) behind a bare number.

## 4. Micro-interactions

- **Cell edit affordance:** hovering an editable cell should show a subtle pencil/focus outline before clicking — users need to know at a glance which of the 12 columns are editable vs. derived/read-only (e.g. `Split` if collapsed into Action Details, or `Commit Status`).
- **Optimistic-save feedback:** since `useTransactionStudioMutations` already does optimistic updates with rollback-on-failure, every cell edit needs a tiny transient state: brief "saving" (subtle, e.g. a dimmed cell background for ~300ms), success = nothing (silence = success, the Notion/Linear convention), failure = the cell reverts *and* shows a small red flash + inline error, not just a silent rollback (the research found rollback currently has zero UI feedback wired — that's a real bug-in-waiting once editing ships).
- **Bulk-action toast with Undo:** any bulk edit/delete completes with a bottom toast: "Updated category for 12 rows · Undo" for ~6 seconds.
- **Row expand on low confidence:** an animated chevron rotation + height transition (not an instant snap) when a row auto-expands to show its flagged field — this is the moment that sells "the system is being careful with your money," worth the animation budget.
- **Fill handle (your list asked whether appropriate):** yes, but scope it tightly — appropriate for `Category`, `Owner`, `Tags` (drag to apply one value down a range of similar rows, exactly the "same merchant appears 10 times, categorize once, drag" use case that's the actual killer feature of statement review). Not appropriate for `Amount`/`Date` (extracted, should never be dragged over) or `Action Details` (structurally can't be filled, it's a compound object). Lock the fill handle to only appear on fill-safe columns rather than implementing it generically and hoping users don't misuse it on Amount.
- **Copy/paste:** scope to single-cell and single-column-range copy/paste for the same fill-safe columns above. Full spreadsheet-grade multi-cell paste (pasting a 2D block from Excel) is a stretch goal, not v1 — don't let it block shipping.

## 5. Visual Hierarchy Improvements

- **Merchant + Amount are the eye's first stop; everything else is secondary.** Right now the only implemented rendering (`DocumentImportRecordsList`) already gets this right by accident (it only renders those two). Preserve that instinct in the full grid: Merchant should be the widest, highest-contrast column; Amount bold/tabular; everything else (Owner, Split, Category, Tags, Notes) should be visually quieter — smaller text or muted chip styling — so the grid doesn't read as 12 columns of equal visual weight, which is what makes spreadsheet clones feel like data dumps instead of workspaces.
- **Suggested vs. confirmed needs a system-wide visual language**, not a per-column decision (see Category/Tags above) — pick one pattern (outline = suggested, filled = confirmed) and apply it everywhere a `StagedSuggestion<T>` backs a field.
- **Confidence should live at the row's left edge**, not scattered — a 2-3px colored bar or dot at the very left of the row (before the Include checkbox, or integrated into it) is a proven pattern (Linear does this with priority) for "scan down the left edge to see what needs attention" without adding a column.
- **Commit Status as the rightmost anchor** — status chips (already have `ClayBadge` + a tone map in `status-labels.ts`, reuse that system rather than inventing new chip styling for the grid).

## 6. Keyboard Interaction Improvements

None of this exists today, so this is greenfield — recommend the Excel/Airtable baseline, not a novel scheme:

- **Arrow keys** move a single-cell focus rectangle (not row-based) between columns/rows.
- **Tab / Shift+Tab** move focus right/left, wrapping to next/previous row at the row boundary (matches Excel/Sheets convention).
- **Enter** opens the focused cell for editing (or commits + moves down one row if already editing, matching Excel).
- **Escape** cancels an in-progress edit without saving.
- **Space** toggles the Include checkbox when a row (not a cell) is focused.
- **Cmd/Ctrl+Z / Shift+Z** — undo/redo, at minimum the single-level toast-based undo from §3.
- **Cmd/Ctrl+A** — select all rows (for bulk actions), distinct from "check all Include boxes."
- **Shift+Click / Shift+Arrow** — range select for bulk operations and fill-handle-adjacent copy/paste.
- **Cmd/Ctrl+C / V** — copy/paste on the fill-safe columns only (§4).
- **"/" or Cmd+K** — jump to search/filter, matching Linear's command-palette-adjacent muscle memory that this feature is explicitly trying to evoke.

None of these are exotic — the point is committing to the standard set now, in the spec, so the eventual grid isn't retrofitted with partial keyboard support later (which is what tends to happen when keyboard nav is treated as post-launch polish).

## 7. Final Recommendations Before Implementation Finishes

1. **Reconcile the two column specs (vision doc vs. your 12-column list) before anyone writes grid code.** Right now there are two documents that disagree, and whichever one a given engineer reads first becomes what gets built.
2. **Design the `Action` / `Action Details` / `Split` cluster as one compound interaction, not three independent columns**, before any cell-editing code is written — this is the highest-complexity, highest-risk part of the whole grid and it's currently the least specified.
3. **Don't build the grid on `FinanceTable` as-is.** It has no cell focus model, no virtualization, no inline editing — extending it will produce something that visually resembles a spreadsheet but can't actually behave like one. Decide now whether that's an acceptable v1 (ship read-mostly, add editing later) or whether new grid infra is needed up front — don't let the decision get made implicitly by whoever starts coding first.
4. **Surface confidence and duplicate signals in the design before anything else new.** These are the two backend capabilities that are fully built, fully tested, and 100% invisible to users today. They are also what make this "Statement Intelligence Workspace" rather than a bulk-edit CRUD grid — without them showing up in the UI, the feature's actual differentiator doesn't exist yet, no matter how polished the grid chrome is.
5. **Decide the Include-checkbox vs. bulk-select-checkbox split now** (§Columns, Include) — this is a one-line spec decision that prevents a confusing UI later.
6. **Treat the validation/pre-import panel as its own designed surface**, not an afterthought bolted onto the footer — it's the gate before money-affecting writes happen and deserves the same design attention as the grid itself.
7. **Ship keyboard navigation and the single-level undo toast in v1, not as follow-up work.** Both are cheap relative to the grid infrastructure itself, and retrofitting keyboard nav onto an existing cell-editing implementation is meaningfully more expensive than designing it in from the start.
