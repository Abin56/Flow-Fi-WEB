# Parity Matrix

### Flutter ↔ Web behavioral tracking — authoritative, living document

**Purpose:** Flutter is the canonical behavioral source for every module the two apps share (Architecture v1.0 §1: "One brain, many surfaces"; user directive: "Keep Flutter as the canonical behavioral source"). This document exists so the Web implementation never silently drifts from it. Update it in the same change that adds or modifies a ported module — a module without a current row here is not considered verified, regardless of how much test coverage it has.

**A critical scope note, stated up front so this document isn't misread:** two very different kinds of "Web implementation" exist in this repository, and they get graded against different bars:

1. **Ported modules** (`Account`, `Transaction`, the finance engines, the repository layer) — these exist in Flutter already and Web's job is to be behaviorally identical. Flutter is the spec.
2. **Financial Document Intelligence Engine modules** (everything under `lib/statement-intelligence/`, `functions/src/`, the new `lib/models/{financial-document,document-import,merchant-mapping,document-type-registry}.ts`) — this is a **new capability that does not exist in Flutter yet** (confirmed in `docs/adr/ADR-002`: `lib/models/credit-card.ts` "does not exist yet" on the Flutter side either, per the mock-data file's own comment). There is nothing to have parity *with* for these — Flutter compatibility here means something different: **schema/contract compatibility** (will Flutter be able to read what Web writes, without Web having to guess Flutter's eventual shape). That distinction is tracked per-row below, not assumed.

## How to update this document

- **New ported module (Part 1):** add a row the same change that adds the TypeScript file. If you have NOT independently verified it against real Dart source, write "Not verified" — do not write "Complete" in the Behaviour-verified column based on the code comment alone; that column asserts an independent check happened, not that a comment claims one should have.
- **New Financial Document Intelligence Engine module (Part 2):** add a row noting whether it introduces new Firestore schema (and therefore carries a Flutter-compatibility risk to flag) or is purely server-internal (and therefore doesn't).
- **Status values:** `Not Started` / `Partial` / `Complete`. `Complete` means the module fully implements what it's supposed to for its current milestone scope — not that the whole eventual feature is done.
- Do not remove a row when a module changes — update it in place, and if behavior changes in a way that could affect Flutter compatibility, that's exactly the kind of finding that belongs in an ADR (per the standing process), cross-referenced from this row.
